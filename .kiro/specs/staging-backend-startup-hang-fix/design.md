# Staging Backend Startup Hang Bugfix Design

## Overview

The staging backend hangs indefinitely during TypeORM initialization due to `synchronize: true` performing heavy schema introspection in non-local environments. This design transitions staging/production to migration-based schema management while preserving automatic synchronization for development. The fix involves: (1) environment-based `synchronize` toggle in `database.module.ts`, (2) TypeORM migration infrastructure with DataSource configuration, (3) deployment workflow integration to run migrations before container start, (4) npm scripts for migration management, and (5) developer documentation for the new workflow.

## Glossary

- **Bug_Condition (C)**: The condition that triggers the startup hang - when staging/production uses `synchronize: true`
- **Property (P)**: The desired behavior - backend completes startup within 30 seconds using migration-based schema management
- **Preservation**: Development/test behavior that must remain unchanged - continues using `synchronize: true` for automatic schema updates
- **bootstrap()**: The NestJS entry function in `src/main.ts` that initializes the application
- **DatabaseModule**: The TypeORM configuration module in `src/shared/common/persistence/database.module.ts`
- **NODE_ENV**: Environment variable that determines runtime environment (development, staging, production, test)
- **synchronize**: TypeORM option that automatically creates/updates database schema on startup (slow in production)
- **DataSource**: TypeORM CLI configuration object for running migrations
- **Migration**: SQL schema change file generated by TypeORM that can be applied incrementally

## Bug Details

### Bug Condition

The bug manifests when the backend starts in staging or production environment with TypeORM's `synchronize: true` configuration. The `DatabaseModule.forRootFromEnv()` factory function does not consider the environment when setting the `synchronize` option, causing TypeORM to perform expensive schema introspection operations that block the event loop. The health check endpoint remains unreachable because the HTTP server never binds to port 3030, as the initialization phase never completes.

**Formal Specification:**

```
FUNCTION isBugCondition(env)
  INPUT: env of type EnvironmentConfig
  OUTPUT: boolean

  RETURN (env.NODE_ENV = "staging" OR env.NODE_ENV = "production")
         AND env.DATABASE_SYNCHRONIZE = true
         AND backend_startup_time > 30_seconds
END FUNCTION
```

### Examples

- **Staging deployment on 2025-01-XX**: Backend container started, TypeORM logged "Postgres enabled (synchronize=true)", container remained in "Up 2 minutes (unhealthy)" state for 120+ seconds, health check returned "Connection reset by peer", deployment failed with "Backend healthcheck failed after 60 attempts"
- **Local development**: Backend starts with `NODE_ENV` unset, TypeORM uses `synchronize: true`, startup completes in 3 seconds, health check returns HTTP 200
- **Production deployment (hypothetical)**: If production were configured with `synchronize: true`, would exhibit same hang as staging
- **Edge case - test environment**: Tests run with `NODE_ENV=test`, should preserve `synchronize: true` behavior for fast test setup

## Expected Behavior

### Preservation Requirements

**Unchanged Behaviors:**

- Development environment (NODE_ENV='development' OR NODE_ENV unset) must continue using `synchronize: true`
- Test environment (NODE_ENV='test') must continue using `synchronize: true`
- Entity registration must continue loading exactly 48 entity classes from `PERSISTED_ENTITIES`
- Database connection parameters must continue using values from `app.config.ts` database section
- TypeORM repository operations (findOne, save) must continue functioning identically
- Developer workflow for adding new entity properties in local dev must continue without requiring migration files

**Scope:**
All inputs that do NOT involve staging/production environments should be completely unaffected by this fix. This includes:

- Local development startup behavior
- Test suite execution
- Developer experience when modifying entity schemas
- In-memory repository fallback when `DATABASE_ENABLED=false`

## Hypothesized Root Cause

Based on the bug description and observed behavior, the most likely issues are:

1. **Unconditional Schema Synchronization**: The `DatabaseModule.forRootFromEnv()` function sets `synchronize` from `cfg?.synchronize ?? true` without considering `NODE_ENV`. Even if `.env.staging` sets `DATABASE_SYNCHRONIZE=false`, the default fallback is `true`, and the environment variable may not be read correctly from the staging .env file.

2. **Missing Environment-Based Logic**: There is no conditional logic in `database.module.ts` that reads `NODE_ENV` and adjusts `synchronize` accordingly. The module expects `DATABASE_SYNCHRONIZE` to be explicitly set in environment variables, but the staging .env file may not contain this variable, or it may not be loaded in the Docker container context.

3. **Incomplete Migration Infrastructure**: While `data-source.ts` exists and migration scripts are defined in `package.json`, the deployment workflow (`deploy-staging.yml`) does not execute migrations before starting the backend container. Additionally, the migrations directory may not exist or may be empty, so even if synchronize were disabled, the database schema would not be initialized.

4. **DataSource Configuration Gap**: The existing `data-source.ts` file has an empty `entities: []` array, which means TypeORM CLI cannot generate migrations that capture the current schema. The DataSource needs to import and register the same 48 entities from `database.module.ts`.

## Correctness Properties

Property 1: Bug Condition - Staging Uses Migrations Not Synchronize

_For any_ backend startup where the environment is staging or production (`NODE_ENV` is "staging" or "production"), the fixed bootstrap function SHALL set TypeORM `synchronize` option to `false`, SHALL execute migrations during deployment before container start, SHALL complete initialization within 30 seconds, SHALL bind to port 3030, AND SHALL respond to health checks with HTTP 200 within 2 seconds.

**Validates: Requirements 2.1, 2.2, 2.3, 2.4, 2.5, 2.6, 2.7, 2.8**

Property 2: Preservation - Development Auto-Sync Unchanged

_For any_ backend startup where the environment is development or test (`NODE_ENV` is "development", "test", or unset), the fixed bootstrap function SHALL produce exactly the same behavior as the original function, setting TypeORM `synchronize` option to `true` and applying schema changes automatically without requiring migration files.

**Validates: Requirements 3.1, 3.2, 3.3, 3.4, 3.5, 3.6, 3.7, 3.8, 3.9**

## Testing Strategy

### Validation Approach

The testing strategy follows a two-phase approach: first, surface counterexamples that demonstrate the bug on unfixed code, then verify the fix works correctly and preserves existing behavior.

### Exploratory Bug Condition Checking

**Goal**: Surface counterexamples that demonstrate the bug BEFORE implementing the fix. Confirm or refute the root cause analysis. If we refute, we will need to re-hypothesize.

**Test Plan**: Write property-based tests that simulate backend startup in different environments with different configurations. Run these tests on the UNFIXED code to observe failures and understand the root cause.

**Test Cases**:

1. **Staging Startup with Synchronize True Test**: Create a mock environment with `NODE_ENV=staging` and `DATABASE_SYNCHRONIZE=true`, simulate `bootstrap()`, assert that startup completes within 30 seconds (will FAIL on unfixed code - exceeds timeout)

2. **Production Startup with Synchronize True Test**: Create a mock environment with `NODE_ENV=production` and `DATABASE_SYNCHRONIZE=true`, simulate `bootstrap()`, assert that startup completes within 30 seconds (will FAIL on unfixed code - exceeds timeout)

3. **Staging Healthcheck Failure Test**: Mock the deployment workflow health check logic, send GET requests to `/api/health` every 2 seconds for 60 attempts, assert that at least one attempt receives HTTP 200 within 120 seconds (will FAIL on unfixed code - all attempts timeout)

4. **TypeORM Log Analysis Test**: Capture TypeORM initialization logs during staging startup, assert that log contains "Schema synchronization completed" within 90 seconds (will FAIL on unfixed code - never emits this log)

**Expected Counterexamples**:

- Backend startup in staging environment with synchronize:true hangs for 120+ seconds
- Health check endpoint never becomes available because port 3030 never binds
- TypeORM logs "Postgres enabled (synchronize=true)" but never logs "Schema synchronization completed"
- Possible root causes: synchronize introspection is blocking, large schema causes expensive queries, database connection pool exhausted

**Implementation Note**: These exploratory tests are MOCK tests that simulate the bug condition without actually hanging for 120 seconds. Use Jest's `jest.setTimeout()` and `jest.useFakeTimers()` to speed up time-based assertions. The goal is to validate that the bug condition logic correctly identifies the problematic configuration, not to reproduce the full 120-second hang.

**Goal**: Verify that for all inputs where the bug condition holds, the fixed function produces the expected behavior.

**Test Plan**: After implementing the fix, run integration tests in a Docker environment that simulates staging configuration. Verify that migrations are applied, synchronize is disabled, and startup completes quickly.

**Test Cases**:

**Goal**: Verify that for all inputs where the bug condition does NOT hold, the fixed function produces the same result as the original function.

**Pseudocode:**


- It provides strong guarantees that behavior is unchanged for all non-buggy inputs

## Migration System Architecture

### DataSource Configuration

**Purpose**: Provide TypeORM CLI with database connection and migration metadata.

**Location**: `apps/backend/src/shared/common/persistence/data-source.ts`

**Structure**:

```typescript
import 'reflect-metadata';
import * as dotenv from 'dotenv';
import { DataSource } from 'typeorm';
import { PERSISTED_ENTITIES } from './entities';

dotenv.config();

export default new DataSource({
  type: 'postgres',
  host: process.env.POSTGRES_HOST ?? 'localhost',
  port: parseInt(process.env.POSTGRES_PORT ?? '5432', 10),
  username: process.env.POSTGRES_USER ?? 'alpha_meta_token_scanner',
  password: process.env.POSTGRES_PASSWORD ?? 'alpha_meta_token_scanner',
  database: process.env.POSTGRES_DB ?? 'alpha_meta_token_scanner',
  entities: PERSISTED_ENTITIES, // CHANGED: was [], now includes all 48 entities
  migrations: [
    'src/shared/common/persistence/migrations/*.ts',
    'dist/src/shared/common/persistence/migrations/*.js',
  ],
  migrationsTableName: 'typeorm_migrations',
  synchronize: false, // Always false for CLI - migrations handle schema
  logging: false,
});
```

**Key Points**:

- Loads environment variables from `.env` via dotenv
- Uses `POSTGRES_*` environment variables (different from runtime `DATABASE_*` variables)
- Entities array must include all 48 TypeORM entities for migration generation to work
- Migrations paths include both `.ts` (for generation) and `.js` (for execution from dist)
- `synchronize: false` because migrations handle schema changes
- `migrationsTableName: 'typeorm_migrations'` tracks which migrations have been applied

### Migration Directory Structure

**Location**: `apps/backend/src/shared/common/persistence/migrations/`

**Naming Convention**: `{timestamp}-{description}.ts`

**Example**: `1736729400000-InitialSchema.ts`

**File Structure**:

```typescript
import { MigrationInterface, QueryRunner } from 'typeorm';

export class InitialSchema1736729400000 implements MigrationInterface {
  name = 'InitialSchema1736729400000';

  public async up(queryRunner: QueryRunner): Promise<void> {
    // Generated CREATE TABLE statements for all 48 entities
    await queryRunner.query(`CREATE TABLE "kol" (...)`);
    await queryRunner.query(`CREATE TABLE "canonical_token_call" (...)`);
    // ... 46 more tables
  }

  public async down(queryRunner: QueryRunner): Promise<void> {
    // Generated DROP TABLE statements in reverse order
    await queryRunner.query(`DROP TABLE "canonical_token_call"`);
    await queryRunner.query(`DROP TABLE "kol"`);
    // ... 46 more drops
  }
}
```

**Key Points**:

- Class name includes timestamp for uniqueness: `InitialSchema1736729400000`
- Filename matches class name: `1736729400000-InitialSchema.ts`
- `up()` method applies the migration (CREATE TABLE, ADD COLUMN, etc.)
- `down()` method reverts the migration (DROP TABLE, DROP COLUMN, etc.)
- Generated migrations include all schema changes TypeORM detected by diffing entities against database

### Environment Detection Logic

**Purpose**: Determine at runtime whether to use `synchronize: true` (dev/test) or `synchronize: false` (staging/production).

**Location**: `apps/backend/src/shared/common/persistence/database.module.ts`

**Implementation**:

```typescript
function isProductionLikeEnvironment(): boolean {
  const env = process.env.NODE_ENV?.toLowerCase();
  return env === 'staging' || env === 'production';
}

@Module({})
export class DatabaseModule {
  public static forRootFromEnv(): DynamicModule {
    if (!isDatabaseEnabled()) {
      /* ... */
    }

    return {
      module: DatabaseModule,
      imports: [
        TypeOrmModule.forRootAsync({
          inject: [ConfigService],
          useFactory: (config: ConfigService) => {
            const cfg = config.get<AppConfig>('app')?.database;
            const useMigrations = isProductionLikeEnvironment();
            const synchronize = useMigrations
              ? false
              : (cfg?.synchronize ?? true);

            DatabaseModule.logger.log(
              `Postgres enabled (host=${cfg?.host}:${cfg?.port} db=${cfg?.database}, ` +
                `synchronize=${synchronize}, env=${process.env.NODE_ENV ?? 'undefined'}, ` +
                `mode=${useMigrations ? 'migrations' : 'auto-sync'}).`,
            );

            return {
              type: 'postgres' as const,
              // ... connection params
              synchronize,
              // ... other options
            };
          },
        }),
      ],
    };
  }
}
```

**Key Points**:

- `isProductionLikeEnvironment()` checks `NODE_ENV` and returns true for staging/production
- Synchronize setting is determined by environment, NOT by `DATABASE_SYNCHRONIZE` env var
- Logging includes environment name and mode (migrations vs auto-sync) for debugging
- Defaults to auto-sync when `NODE_ENV` is undefined (development behavior)

### NPM Scripts for Migration Management

**Location**: `apps/backend/package.json`

**Scripts**:

```json
{
  "scripts": {
    "typeorm": "typeorm-ts-node-commonjs --dataSource src/shared/common/persistence/data-source.ts",
    "migration:generate": "npm run typeorm -- migration:generate",
    "migration:run": "npm run typeorm -- migration:run",
    "migration:revert": "npm run typeorm -- migration:revert",
    "migration:show": "npm run typeorm -- migration:show"

```

**Usage Examples**:

1. **Generate Initial Migration**:

   ```bash
   npm run migration:generate -- -n InitialSchema
   ```
   - Compares entity definitions against current database schema
   - Generates migration file with timestamp: `1736729400000-InitialSchema.ts`
   - Places file in `src/shared/common/persistence/migrations/`

2. **Apply Pending Migrations**:

   ```bash
   npm run migration:run
   ```
   - Checks `typeorm_migrations` table to see which migrations have been applied
   - Runs all pending migrations in chronological order
   - Updates `typeorm_migrations` table to record applied migrations
   - Idempotent: safe to run multiple times, skips already-applied migrations

3. **Rollback Last Migration**:

   ```bash
   npm run migration:revert
   ```
   - Identifies most recently applied migration from `typeorm_migrations` table
   - Executes the `down()` method to revert schema changes
   - Removes entry from `typeorm_migrations` table
   - Can be run multiple times to revert multiple migrations

4. **Show Migration Status**:
   ```bash
   npm run migration:show
   ```
   - Lists all migration files in chronological order
   - Marks each as "applied" or "pending"
   - Useful for debugging deployment issues

**Key Points**:

- All scripts use `typeorm-ts-node-commonjs` to run TypeScript files directly
- Scripts reference `data-source.ts` which must export a configured DataSource
- Generate command requires `-n` flag to specify migration name
- Run command is idempotent and safe for deployment automation

```yaml
        docker compose -f /opt/onchain-bot-staging/apps/backend/docker-compose.staging.yml logs backend --tail 50
        exit 1
      fi
    done
```

**Rationale**:

- With migrations handling schema updates, backend should start in < 10 seconds
- Reduced timeout fails fast if something is wrong
- Logs include curl output AND backend container logs for debugging

### Workflow for Adding New Migrations

**Scenario**: You need to add a new column `emailVerified` to the `KolEntity`.

**Steps**:

1. **Modify Entity Class**:

   ```typescript
   // apps/backend/src/kol/identity/infrastructure/persistence/typeorm/entities/kol.entity.ts
   @Entity('kol')
   export class KolEntity {
     @PrimaryColumn()
     id: string;

     @Column()
     username: string;

     @Column({ default: false }) // NEW COLUMN
     emailVerified: boolean;
   }
   ```

2. **Generate Migration Locally**:

   ```bash
   cd apps/backend
   npm run migration:generate -- -n AddEmailVerifiedToKol
   ```
   - TypeORM compares entity against local database
   - Generates migration file: `1736729500000-AddEmailVerifiedToKol.ts`
   - Migration includes `ALTER TABLE kol ADD COLUMN emailVerified boolean DEFAULT false`

3. **Review Generated Migration**:

   ```typescript
   // apps/backend/src/shared/common/persistence/migrations/1736729500000-AddEmailVerifiedToKol.ts
   export class AddEmailVerifiedToKol1736729500000 implements MigrationInterface {
     public async up(queryRunner: QueryRunner): Promise<void> {
       await queryRunner.query(
         `ALTER TABLE "kol" ADD "emailVerified" boolean NOT NULL DEFAULT false`,
       );
     }

     public async down(queryRunner: QueryRunner): Promise<void> {
       await queryRunner.query(`ALTER TABLE "kol" DROP COLUMN "emailVerified"`);
     }
   }
   ```

4. **Test Migration Locally**:

   ```bash
   npm run migration:run
   npm run start:dev
   # Verify backend starts without errors
   # Verify new column exists in database
   ```

5. **Commit and Push**:

   ```bash
   git add src/kol/identity/infrastructure/persistence/typeorm/entities/kol.entity.ts
   git add src/shared/common/persistence/migrations/1736729500000-AddEmailVerifiedToKol.ts
   git commit -m "feat: add emailVerified column to KolEntity"
   git push origin feature-branch
   ```

6. **Deployment Applies Migration Automatically**:
   - When feature branch is merged to dev and deployed to staging
   - `deploy-staging.yml` runs `npm run migration:run`
   - New migration is applied before backend container starts
   - Backend starts with updated schema

### Testing Migrations Locally

**Goal**: Verify migration works correctly before pushing to dev/staging.

**Prerequisites**: Local PostgreSQL running, DATABASE_ENABLED=true in .env

**Steps**:

1. **Start from Clean State**:

   ```bash
   # Drop and recreate local database
   dropdb -U alpha_meta_token_scanner alpha_meta_token_scanner
   createdb -U alpha_meta_token_scanner alpha_meta_token_scanner
   ```

2. **Apply All Migrations**:

   ```bash
   cd apps/backend
   npm run migration:run
   ```
   - Should see log: "X migrations have been applied"
   - Should NOT see any errors

3. **Verify Schema**:

   ```bash
   psql -U alpha_meta_token_scanner -d alpha_meta_token_scanner -c "\dt"
   ```
   - Should list all 48 tables
   - Verify your new table/column exists

4. **Start Backend with Synchronize Disabled**:

   ```bash
   # Temporarily override synchronize in .env.dev
   echo "DATABASE_SYNCHRONIZE=false" >> .env.dev
   npm run start:dev
   ```
   - Backend should start without logging schema synchronization
   - Should NOT see "Schema sync completed" in logs
   - If you see schema changes being applied, migration is incomplete

5. **Test Rollback**:

   ```bash
   npm run migration:revert
   # Verify your changes were reverted
   npm run migration:run
   # Verify changes were re-applied
   ```

6. **Restore Auto-Sync for Development**:
   ```bash
   # Remove override
   sed -i '' '/DATABASE_SYNCHRONIZE=false/d' .env.dev
   ```

### Migration Best Practices

1. **Generate Migrations, Don't Write Manually**:
   - Always use `npm run migration:generate` instead of writing SQL by hand
   - TypeORM generates correct SQL dialect for PostgreSQL
   - Generated migrations include proper escaping and type handling

2. **Review Generated Migrations**:
   - Check that `up()` and `down()` methods are inverses
   - Verify column types match entity definitions
   - Look for unexpected schema changes (might indicate entity misconfiguration)

3. **Test Down Migrations**:
   - Always test `npm run migration:revert` locally
   - Ensure rollback leaves database in a consistent state
   - If revert fails, fix the `down()` method before merging

4. **Keep Migrations Small**:
   - One migration per logical change (e.g., "Add email verification")
   - Avoid combining unrelated schema changes in one migration
   - Smaller migrations are easier to review and rollback

5. **Never Edit Applied Migrations**:
   - Once a migration is applied in staging/production, never modify it
   - If you need to fix a migration, create a new migration that corrects it
   - Editing applied migrations breaks migration tracking

6. **Coordinate with Team**:
   - Migrations are sequential - merge conflicts can break order
   - Communicate schema changes in pull request descriptions
   - If two developers generate migrations simultaneously, one will need to regenerate after merge

### Troubleshooting Migration Issues

**Problem**: Migration generation fails with "No changes detected"

**Solution**:

- Verify entity changes are saved
- Ensure `data-source.ts` includes the modified entity in `entities` array
- Check that local database schema matches what TypeORM expects (run `npm run migration:run` first)

**Problem**: Migration fails to apply in staging with "relation already exists"

**Solution**:

- Another migration may have already created the table/column
- Check `npm run migration:show` to see which migrations are applied
- Modify your migration to check if relation exists before creating (use `queryRunner.hasColumn()`)

**Problem**: Backend startup hangs in staging even with migrations

**Solution**:

- Check `NODE_ENV` is set to "staging" in .env.staging
- Verify `database.module.ts` logs show "mode=migrations"
- Check that migrations completed successfully in deploy workflow logs
- Ensure no `DATABASE_SYNCHRONIZE=true` override in .env.staging

**Problem**: Local development auto-sync stopped working after migration changes

**Solution**:

- Verify `NODE_ENV` is NOT set to "staging" or "production" locally
- Remove any `DATABASE_SYNCHRONIZE=false` overrides from .env.dev
- Restart backend and check logs for "mode=auto-sync"
- If still broken, drop local database and let auto-sync recreate schema
